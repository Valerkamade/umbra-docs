# Ведение документации UMBRA

Документация должна отражать актуальные решения и состояние продукта, а не
существовать отдельно от реализации. Изменение требования, модели, API или
диаграммы включает проверку всех связанных артефактов.

## GitHub Flow

Единственная постоянная ветка — `main`. Она содержит актуальную опубликованную
документацию. Ветка `develop` и постоянная ветка `gh-pages` не используются.

Рабочий цикл:

1. Выбрать существующую задачу Jira и перевести её в работу вручную.
2. Обновить локальную `main` и создать тематическую ветку.
3. Внести логически связанное изменение и выполнить локальные проверки.
4. Создать Pull Request в `main` и дождаться успешного CI.
5. Провести самопроверку по шаблону Pull Request.
6. Выполнить **Squash and merge**.
7. Удалить временную ветку; публикация из `main` запускается автоматически.
8. Проверить опубликованный результат и обновить задачу Jira вручную.

Не переписывайте общую историю, не выполняйте force push и не создавайте
искусственные коммиты ради количества.

## Именование веток

Формат:

```text
<type>/<jira-key>-<short-description>
```

Примеры:

```text
chore/UM-44-docs-infrastructure
ci/UM-45-docs-deployment
docs/UM-46-contribution-workflow
docs/UM-48-mvp-scope
fix/UM-53-api-errors
```

Если задача Jira действительно отсутствует, допустима ветка без ключа, например
`chore/setup-docs-infrastructure`. Не придумывайте идентификаторы Jira.

## Conventional Commits

Заголовок коммита пишется на английском языке:

```text
<type>(<scope>): <description>
```

| Тип | Назначение |
| --- | --- |
| `docs` | Изменение документации |
| `feat` | Новая возможность портала |
| `fix` | Исправление ошибки |
| `chore` | Настройка инфраструктуры |
| `ci` | Автоматизация проверок и публикации |
| `build` | Зависимости и сборка |
| `refactor` | Изменение структуры без изменения смысла |
| `style` | Визуальное оформление |
| `test` | Автоматические проверки |

При наличии задачи Jira добавьте ключ в тело коммита:

```text
docs(scope): define MVP boundaries

Describe the confirmed scope and explicit exclusions.

Refs: UM-48
```

Один коммит представляет логически завершённое изменение. Перед фиксацией
проверьте, что в него не попали `site/`, `.cache/`, `.venv/`, секреты или
локальные абсолютные пути.

## Связь с Jira

Проект документации использует существующий проект Jira UMBRA с ключом `UM`.
Отдельный Jira-проект для документации не создаётся. Jira хранит цель и результат
работы, но не журнал каждой технической команды.

Целевая трассировка:

```text
Задача Jira
    → тематическая ветка
    → коммиты с Refs
    → Pull Request
    → CI
    → squash merge в main
    → публикация
```

Рекомендуемый процесс задачи:
`К выполнению → В работе → Проверка → Готово`. Статусы меняются вручную после
фактического достижения соответствующего состояния. Токены Jira не хранятся в
репозитории.

## Pull Request

Содержательные изменения проходят через Pull Request. Название начинается с
ключа задачи, например:

```text
[UM-48] Границы MVP
```

Заполните `.github/pull_request_template.md`: укажите ссылку на Jira, цель,
затронутые артефакты, технические решения, результаты проверок и ограничения.
Pull Request служит для самопроверки и трассировки; обязательное согласование
другим участником не требуется, поэтому число required approvals равно нулю.

Основной способ слияния — **Squash and merge**. Merge commits и rebase merge в
репозитории должны быть отключены. После слияния тематическая ветка удаляется.

## Критерии готовности изменения

Изменение готово к слиянию, когда:

- цель и связь с задачей Jira явно указаны;
- документация соответствует подтверждённым решениям и реализации;
- связанные требования, модели, API и диаграммы не противоречат друг другу;
- используются относительные внутренние ссылки;
- `python -m mkdocs build --strict` завершается успешно;
- `python scripts/check_diagrams.py site` подтверждает корректные SVG;
- CI Pull Request завершён успешно;
- отсутствуют секреты, персональные данные, кэш и результаты сборки;
- ограничения и открытые вопросы зафиксированы в Pull Request.

## Диаграммы

PlantUML запускается только через `compose.yml`. Не используйте публичный сервер
и не добавляйте внешние `!include` без согласованного решения.

Небольшую диаграмму можно хранить inline. Повторно используемый или объёмный
исходник храните в `docs/assets/diagrams/` в UTF-8 и подключайте так:

````markdown
```puml
--8<-- "assets/diagrams/example.puml"
```
````

После изменения диаграммы выполните строгую сборку и SVG-проверку. Диаграмма не
должна вводить неподтверждённые компоненты, интеграции или потоки. Для текущего
монохромного оформления используйте прозрачный фон, чтобы схема была читаема в
светлой и тёмной темах.

## Актуальность связанных артефактов

При изменении поведения продукта проверьте как минимум:

- границы релиза и бизнес-требования;
- функциональные и нефункциональные требования;
- пользовательские сценарии и бизнес-правила;
- модели процессов, архитектуру и модель данных;
- API, интерфейсы, критерии приёмки и историю релиза.

Обновляйте только существующие содержательные артефакты. Не создавайте пустые
страницы и каталоги «на будущее». Если связанный артефакт пока не определён,
зафиксируйте это как ограничение или отдельную согласованную задачу Jira.

## Версионирование

Документация конкретного релиза продукта фиксируется Git-тегом SemVer, например
`v0.1.0`, только после фактической готовности релиза. Тег ставится на коммит в
`main`, соответствующий опубликованной документации. Предварительные теги и
версии сайта через `mike` на текущем этапе не используются.

Текущая структура MkDocs не препятствует последующему подключению нескольких
версий сайта.

## Язык

Проектная документация, Pull Request и итоговые отчёты пишутся на русском языке.
Общепринятые технические термины, идентификаторы, имена веток и сообщения
коммитов сохраняются на английском языке.

## Настройка GitHub после первого успешного CI

Настройки применяет владелец репозитория после первого успешного запуска job
`validate`, чтобы не заблокировать первоначальную публикацию.

### Pull Requests

В **Settings → General → Pull Requests**:

- отключить **Allow merge commits**;
- включить **Allow squash merging**;
- отключить **Allow rebase merging**;
- включить **Automatically delete head branches**.

### Ruleset для main

В **Settings → Rules → Rulesets → New branch ruleset** создать активный ruleset:

1. Название: `Protect main`.
2. Target branches: **Include default branch** или шаблон `main`.
3. Включить **Restrict deletions**.
4. Оставить **Block force pushes** включённым.
5. Включить **Require a pull request before merging** и установить
   **Required approvals: 0**.
6. Включить **Require conversation resolution before merging**.
7. Включить **Require linear history**.
8. Включить **Require status checks to pass** и выбрать появившийся после первого
   CI статус `validate`; требование актуальности ветки можно оставить выключенным
   для одиночного проекта.
9. Не добавлять bypass и ограничения обновлений, которые заблокируют владельца.
10. Сохранить ruleset и проверить цикл на следующем Pull Request.

Ruleset не применяется до появления успешного статуса `validate` и завершения
первичной настройки Pages.
